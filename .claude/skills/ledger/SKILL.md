# 制作台帳を更新する

## この台帳が何なのか

みたもさん（チャンネル運営者）と共有している進捗ページ。
**制作側とみたもさんの間で、唯一の「いまどうなっているか」の窓口**になっている。

- 元ファイル：`docs/ledger.html`
- 公開URL：**https://claude.ai/code/artifact/58e12afd-b45c-4465-b217-4a7c98f1c160**

みたもさんはこのリンクをブックマークしている前提で運用する。
だから**URLは絶対に変えない**。

## 手順

### 1. いまの状態を実際に確かめる

記憶や会話の流れではなく、現物を見る。台帳が実態とずれると、
みたもさんが見ている情報が嘘になる。

```bash
git log --date=format:'%Y-%m-%d' --pretty='%ad|%s' | head -10
grep -rn 'TODO' data/ content/ tools/build.ts tools/build-pages.ts | cut -c1-100
sed -n '/^## まだ決まっていないこと/,/^これらは/p' CLAUDE.md
```

`data/recipes.ts` のレシピ件数と `ready: false` の数も見ておく。
（`dist/` の中は組み立てで作られるものなので、数えるなら元データのほうを見る）

### 2. 4か所を直す

| 場所 | 直すこと |
|---|---|
| 冒頭の `.asof` | 最終更新の日付 |
| 冒頭の `.tally` | 実装済み・未実装・確認待ちの件数。**節の中身と必ず合わせる** |
| 該当する節 | 済んだ項目を「未」から「済」へ。新しく分かったことを足す |
| 「更新履歴」の節 | いちばん上に1行足す |

状態は3つ。`c-done`（済・緑）、`c-todo`（未・灰）、`c-wait`（待・朱）。
**`c-wait` は「こちらが待たされている」ものだけ**に使う。
みたもさんの返事待ち、トークン待ちなど。自分の作業残りは `c-todo`。

### 3. 更新履歴の書き方

みたもさんが**前に見たときから何が変わったか**が分かればよい。

- よい：`レシピガチャを追加。PR投稿を自動投稿の対象外に`
- わるい：`fix: refactor assets/script.js and update styles`

コミットメッセージをそのまま貼らない。1日に何回作業しても、
みたもさんから見て意味のあるまとまりで1行にする。

### 4. 同じURLで再公開する

Artifact ツールに `file_path` と **`url`（上のURL）** の両方を渡す。
`label` に短い変更名を入れておくと、あとで版を追える。

**`url` を渡し忘れると別のページが増える。**
みたもさんは古いほうを見続けることになり、しばらく誰も気づかない。
ここが一番の事故なので、公開前に必ず確認する。

### 5. コミットする

```bash
git add docs/ledger.html CLAUDE.md && git commit -m "台帳を更新：<何を>"
```

## 書かないこと

- **誰がいつ何を直したかの詳細**。Git の履歴が持っている。二重管理すると必ずずれる
- 実装の中身（クラス名、関数名）。みたもさんが読む前提のページなので、
  画面で何ができるようになったかを書く
- 憶測。「たぶん来週できる」ではなく、決まっていることだけ

## 気をつけること

みたもさんへの依頼（E節）は、**増えたら必ず先頭に近い側へ**。
待たせている項目が下に埋もれると、いつまでも返事が来ない。

件数（`.tally`）と中身がずれたまま公開すると、
台帳そのものが信用されなくなる。数え直してから公開すること。
