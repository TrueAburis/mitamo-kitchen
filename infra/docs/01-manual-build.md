# AWS を手で作る（フェーズ1）

アカウントを作るところから、作って、確かめて、壊すところまで。

**なぜ手で作るのか。** このあと同じものを Terraform で書く。
先に手を動かしておくと、コードの1行ずつが何のためにあるか分かる。
手で作ったときに**間違えた箇所**が、そのままコード化する理由になる。

> **画面の文言は変わる。** ここに書いたボタン名が違っていたら、
> 画面に出ている言葉を優先すること。**入れる値のほうが本体**で、
> たどり方は変わってもよい。迷ったら文言をそのまま伝えてほしい。

---

## 全体の流れ

```
準備        1〜5    アカウント・安全装置・CLI
手で作る    6〜13   S3 → Function → ヘッダー → 配信 → 権限
確かめる    14      動作確認と、記録を残す
壊す        15      依存の逆順に削除
```

所要時間の目安：準備40分／構築60〜90分（うち待ち時間15分）／削除20分

費用：ドメインを付けなければ Route53 は作られない。
S3 と CloudFront はこの規模なら無料枠にほぼ収まる。
ただし**保証はできない**ので、手順3の予算アラートは必ず入れること。

### 作るものの関係

```
        ┌──────────────┐
閲覧者 →│  CloudFront  │→ S3（非公開）
        └──────────────┘
           ↑ ↑ ↑
           │ │ └─ レスポンスヘッダーポリシー（手順8）
           │ └─── CloudFront Function（手順7）
           └───── OAC ＋ バケットポリシー（手順9・10）

GitHub Actions →[OIDC]→ IAMロール →（書き込み）→ S3
                手順11      手順12
```

# 準備

## 1. AWS アカウントを作る

すでにあれば飛ばす。

### 言葉

**ルートユーザー** … アカウントを作ったときのメールアドレスで入る、最上位の権限。
**何でもできてしまう**ので、日常作業では使わない。手順4で別のユーザーを作る。

### 手順

1. https://aws.amazon.com/jp/ から「無料アカウントを作成」
2. **ルートユーザーのメールアドレス**と、アカウント名を入れる
   - このメールアドレスがアカウントの本体になる。**自分が確実に受け取れるもの**にする
3. メール宛の確認コードを入れる
4. ルートユーザーのパスワードを決める
5. 連絡先情報（個人 or ビジネス）を入れる
6. **クレジットカード情報**を入れる
   - 無料枠でも登録は必須。本人確認のため少額（1ドル程度）の与信が立つことがある。請求ではない
7. 電話番号の確認（SMS または自動音声で、画面のコードを入力）
8. **サポートプランは「ベーシック - 無料」** を選ぶ

### 気をつけること

- 有効化に**数分〜数時間**かかることがある。「アカウントを有効化しています」と出たら待つ
- 有効化前はサービスを作れない。焦らない
- カード情報の入力は**自分で行う**こと。人に代行してもらわない

## 2. ルートアカウントに MFA

**MFA（多要素認証）** … パスワードに加えて、スマホのアプリが出す6桁の数字を要求する仕組み。
これが無いと、**メールとパスワードだけでアカウント内の全部を消せる**状態が続く。

### 手順

1. コンソール右上の**アカウント名をクリック** → 「セキュリティ認証情報」
2. 「多要素認証 (MFA)」の欄で「**MFA デバイスの割り当て**」
3. デバイス名（`phone` など、何でもよい）を入れる
4. MFA デバイスの種類で「**認証アプリケーション**」を選ぶ
5. QRコードが出る → **Google Authenticator でスキャン**
6. アプリに表示される6桁を入れる
   - **連続する2つのコード**を求められる。1つ目を入れたあと、
     アプリの数字が変わるまで（最大30秒）待って、2つ目を入れる

### 気をつけること

- **スマホを無くすとログインできなくなる。** 復旧はサポート経由で手間がかかる。
  可能なら認証アプリのバックアップ機能を有効にしておく
- ここから先、**ルートユーザーでの作業は終わり**。手順4で作るユーザーに切り替える
  - ただし手順3（予算）だけはルートのまま進めてよい。IAMユーザーは既定で請求画面が見えないため

## 3. 予算アラート（先にやる）

**手で作ると消し忘れが起きる。** 気づける状態にしてから先へ進む。

### 先に言葉の意味

画面でつまずくのはこの3つ。

| 言葉 | 意味 |
|---|---|
| **テンプレート** | よくある設定の型。選ぶと細かい項目が埋まった状態で始まる。自分で1から決める「カスタマイズ」もあるが、今回はテンプレートで足りる |
| **予算（予算額）** | 「月にいくらまで」の基準額。**超えたら止まるわけではない**。この額を基準にして、何％に達したら知らせるかを決めるためのもの |
| **スコープ** | どの費用を数えるか。サービス別・リージョン別・タグ別に絞れる。**今回は絞らない（全部）** |

**予算は課金を止めない。** 知らせるだけ。AWS に「使いすぎたら自動で止める」仕組みは無い。
だから早めに気づくことがすべて。

### 手順

**Budgets は請求の画面にある。** コンソール上部の検索窓に `Budgets` と入れて開く。
（リージョンの選択は関係ない。請求は全体で1つ）

1. **「予算を作成」**
2. **予算タイプ** で **「テンプレートを使用（シンプル）」** を選ぶ
3. テンプレートの一覧から **「月次コスト予算」** を選ぶ

そのあと入れるのはこれだけ。

| 項目 | 入れる値 |
|---|---|
| 予算名 | `monthly-5usd`（何でもよい） |
| 予算額 | **5**（USD） |
| メールの送信先 | 自分のメールアドレス |

作成を押して終わり。**スコープは出てこない**（テンプレートが「全サービス」で埋めてくれる）。

### これで何が起きるか

月次コスト予算のテンプレートは、**3つの通知を自動で仕込む**。

| いつ | 何に対して |
|---|---|
| 予算額の 85% に達したとき | 実際に使った額 |
| 予算額の 100% に達したとき | 実際に使った額 |
| 月末に 100% を超えそうなとき | **予測額** |

3つめが効く。使い切る前に、**このままだと超えそうだ**という段階で届く。

### カスタマイズを選んでしまった場合

「カスタマイズ（アドバンスト）」に進んでしまったら、こう埋める。

| 項目 | 値 |
|---|---|
| 予算タイプ | **コスト予算** |
| 期間 | 月次 |
| 予算の更新タイプ | **固定** |
| 予算額 | 5 USD |
| **スコープ** | **すべての AWS サービス**（フィルターを何も足さない） |
| アラートのしきい値 | 80% ／ トリガーは **実績** ／ 送信先は自分のメール |

しきい値はあとから足せる。まず1つ作ってしまってよい。

### 気をつけること

- **予算は2つまで無料。** 3つ目から1日あたり数円かかる。1つで足りる
- **費用の反映は1日ほど遅れる。** 作った直後に $0.00 でも正常
- **メールが届くか、後で確かめる。** 迷惑メールに入ることがある
- **IAM ユーザーからは請求画面が見えないことがある。** 既定で塞がっているため。
  手順4で作ったユーザーで見たくなったら、ルートで
  「アカウント」→「IAM ユーザー/ロールによる請求情報へのアクセス」を有効にする

### もっと早く気づきたいなら

テンプレートには **「ゼロ支出予算」** もある。
**1円でも課金されたら知らせる**もので、「無料枠に収まっているはず」を確かめたいときに向く。

ただし今回は CloudFront と S3 で数円は発生するので、すぐ鳴る。
鳴ることで「課金が始まった」と分かるのは利点だが、
鳴りっぱなしになるのが嫌なら月次5USDだけでよい。

## 4. 作業用の IAM ユーザーとアクセスキー

### なぜ必要か

ルートユーザーは強すぎる。漏れたときの被害が全部に及ぶ。
**日常作業は権限を分けたユーザーで行う**のが基本。

**アクセスキー** … CLI やプログラムから AWS を操作するための鍵。
パスワードと同じ重さで扱う。**画面に貼らない、チャットに貼らない、リポジトリに入れない。**

### ユーザーを作る

IAM → ユーザー → **ユーザーを作成**

1. **ユーザー名**：`aburis-admin` など
2. 「**AWS マネジメントコンソールへのユーザーアクセスを提供する**」
   - チェックすると、このユーザーでコンソールにもログインできる。**チェックを勧める**
     （ルートを使わずに済むようになる）
   - チェックした場合、パスワードの設定と「次回ログイン時にパスワード変更を要求」の選択が出る
3. 「次へ」→ **許可のオプション**
   - 「**ポリシーを直接アタッチする**」を選ぶ
   - 一覧から `AdministratorAccess` を探してチェック
4. 確認して「**ユーザーの作成**」

> **なぜ AdministratorAccess なのか。** テスト用の割り切り。
> 本番運用なら権限を絞るが、CloudFront・IAM・S3 をまたいで作るので
> 最初から絞ると「権限が足りない」で何度も止まる。
> **絞るのは、何が必要か分かってから**でよい。この判断自体が説明材料になる。

### アクセスキーを作る

ユーザーを作っただけでは CLI は使えない。**作成後に別途発行する。**

1. 作ったユーザーの名前をクリック
2. 「**セキュリティ認証情報**」タブ
3. 「アクセスキー」の欄で「**アクセスキーを作成**」
4. 主な使用方法で「**コマンドラインインターフェイス (CLI)**」を選ぶ
   - 「代替案を検討してください」という警告が出る。正論だが、今回は CLI で進める
   - 下の「**上記のレコメンデーションを理解し…**」にチェック
5. 説明タグは空でよい
6. 「アクセスキーを作成」

**アクセスキーID** と **シークレットアクセスキー** が表示される。

⚠️ **シークレットキーはこの画面でしか見られない。** 閉じたら二度と表示されない
（無くしたら作り直しになる）。閉じる前にコピーするか、`.csv` をダウンロードする。

⚠️ **このキーを誰にも渡さない。** 次の手順で自分の PC に直接入れる。

## 5. AWS CLI を入れて、認証を通す

### 入れる

```bash
winget install Amazon.AWSCLI
```

入れたら**ターミナルを開き直す**（PATH の反映のため）。

```bash
aws --version
```

`aws-cli/2.x.x ...` のように出れば成功。

**`aws` が見つからないと言われたら**

- ターミナルを開き直したか確認する
- それでも駄目なら、PC を再起動するか、
  https://awscli.amazonaws.com/AWSCLIV2.msi を直接ダウンロードして入れる

### 認証を通す

```bash
aws configure
```

4つ聞かれる。

| 聞かれるもの | 入れるもの | 意味 |
|---|---|---|
| AWS Access Key ID | 手順4のキーID | 誰であるか |
| AWS Secret Access Key | 手順4のシークレットキー | その証明（入力しても画面に出ない） |
| Default region name | `us-east-1` | 既定でどこに作るか |
| Default output format | `json` | 結果の表示形式 |

入れた内容は `C:\Users\<あなた>\.aws\credentials` に平文で保存される。
**このファイルもパスワード同然**なので、共有フォルダに置かない。

### 確認

```bash
aws sts get-caller-identity
```

```json
{
    "UserId": "AIDA...",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/aburis-admin"
}
```

こう返れば成功。**`Account` の12桁は後で何度も使う**のでメモしておく。

> **なぜ us-east-1 なのか。** あとで独自ドメインを付けるとき、
> CloudFront の証明書（ACM）は仕様上 us-east-1 にしか置けない。
> S3 自体はどこでもよいが、最初から同じ場所に寄せておく。

# 手で作る

作る順番は依存関係で決まっている。この順で進める。

```
6. S3 バケット
7. CloudFront Function        ← 配信より先に作る（配信から参照するため）
8. レスポンスヘッダーポリシー   ← 同上
9. CloudFront ディストリビューション ＋ OAC
10. S3 バケットポリシー         ← 配信のIDが要るので配信の後
11. OIDC プロバイダ
12. IAM ロール                  ← バケット名と配信IDが要るので最後
13. GitHub 側の設定
```

**ここから先は、手順4で作ったユーザーでログインして作業する**（ルートではなく）。

## 6. S3 バケット

**バケット** … ファイルの置き場所。フォルダのようなもの。
名前は**世界中で一意**でなければならない（他人が使っている名前は取れない）。

### 作る

S3 → **バケットを作成**

| 項目 | 値 |
|---|---|
| AWS リージョン | **us-east-1**（米国東部 バージニア北部） |
| バケット名 | `mitamo-kitchen-site-<自分で決めた文字>` |
| オブジェクト所有者 | ACL 無効（推奨）← 既定のまま |
| **パブリックアクセスをすべてブロック** | **オン（4つとも）**← 既定のまま |
| バケットのバージョニング | **有効にする**（既定は「無効にする」ので**変更が要る**） |
| デフォルトの暗号化 | Amazon S3 マネージドキー (SSE-S3) ← 既定のまま |

バケット名の決まり

- 小文字・数字・ハイフンのみ（大文字とアンダースコアは使えない）
- 3〜63文字
- 例：`mitamo-kitchen-site-20260911`

### ライフサイクルルールを足す

バケットを作ったあと、そのバケットを開いて **「管理」タブ** → 「ライフサイクルルールを作成する」

| 項目 | 値 |
|---|---|
| ルール名 | `expire-old-versions` |
| 適用範囲 | **バケット内のすべてのオブジェクトに適用** |
| ルールアクション | 「**オブジェクトの非現行バージョンを完全に削除**」にチェック |
| オブジェクトが非現行になってからの日数 | **30** |

### なぜこうするのか

**パブリックアクセスを全部ブロック** … 静的サイトで最も多い事故が
「バケットを公開設定にして、意図しないファイルまで見られる」。
CloudFront 経由でしか読めない形にすれば、**構造としてその事故が起きない**。

**バージョニング＋30日で削除** … 上書き事故から戻せるようにする。
ただし古い版を無限に持つと課金が増えるので、30日で切る。

### 気をつけること

- ここでは **静的ウェブサイトホスティングを有効にしない。** よく混同されるが、
  あれを使うとバケットを公開する必要が出る。今回は CloudFront + OAC で配るので不要

## 7. CloudFront Function

**CloudFront Function** … 配信の入口で動く小さなプログラム。
リクエストの URL を書き換えるような、軽い処理だけができる。

### 作る

CloudFront を開く → 左のメニューの「**関数**」 → **関数を作成**

1. 関数名：`rewrite-index`
2. ランタイム：**cloudfront-js-2.0**
3. 「関数を作成」

編集画面の「**ビルド**」タブに、この中身を貼る（既定のコードは消す）。

```js
function handler(event) {
  var request = event.request;
  var uri = request.uri;
  if (uri.endsWith('/')) {
    request.uri = uri + 'index.html';
  } else if (!uri.includes('.')) {
    request.uri = uri + '/index.html';
  }
  return request;
}
```

4. 「**変更を保存**」
5. 「**発行**」タブ → 「**関数を発行**」

⚠️ **発行しないと配信から使えない。** 保存しただけでは下書き状態。
手順9で関数を選ぼうとしたときに出てこなかったら、たいていここ。

### 動くか試す（任意）

「**テスト**」タブで、URL パスに `/en/` を入れて実行すると、
`request.uri` が `/en/index.html` に変わるのが見られる。

### なぜ要るのか

S3 は「ディレクトリ」という考え方を持たない。
`/en/` で来たリクエストに `/en/index.html` を返す仕組みが無いので、ここで補う。

開発用の `serve.ps1` にも同じ処理を入れてあり、**手元と本番の挙動を合わせている**。
片方だけ動く状態を作らないため。

## 8. レスポンスヘッダーポリシー

**レスポンスヘッダーポリシー** … 配信するときに、
どのページにも共通で付ける HTTP ヘッダーの決まりごと。

### 作る

CloudFront → 左メニューの「**ポリシー**」 → 「**レスポンスヘッダー**」タブ → **レスポンスヘッダーポリシーを作成**

名前：`mitamo-kitchen-security-headers`

**セキュリティヘッダー**の欄で、以下を有効にして値を入れる。
どれも「**オリジンの上書き**（Override）」にチェックを入れる。

| ヘッダー | 設定 | 何のため |
|---|---|---|
| Strict-Transport-Security | max-age **31536000** ／ サブドメインを含める **オン** ／ preload **オン** | 次回から必ず HTTPS で来させる |
| X-Content-Type-Options | 有効にするだけ（`nosniff` が入る） | 中身を勝手に別の型として解釈させない |
| X-Frame-Options | **DENY** | 他サイトの枠に埋め込ませない |
| Referrer-Policy | **strict-origin-when-cross-origin** | 外部サイトに詳しいURLを渡さない |
| Content-Security-Policy | 下記を1行で | どこから読み込んでよいかを限定する |

Content-Security-Policy に貼る値:

```
default-src 'self'; img-src 'self' data: https:; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; script-src 'self'; frame-src https://docs.google.com https://www.instagram.com; form-action 'self' https://docs.google.com; base-uri 'none'; object-src 'none'; frame-ancestors 'none'
```

### なぜ `script-src 'self'` まで絞れるのか

このサイトには**インラインの `<script>` が1つも無い。**
素のHTMLで組んできた副産物で、普通のサイトは `'unsafe-inline'` を外せない。
**面接で聞かれたらここを話すとよい。**

`style-src` に `'unsafe-inline'` が残るのは、属性で書いたスタイルが数箇所あるため。
`frame-src` の2つは、お仕事のご依頼フォーム（Google）とレシピ動画（Instagram）。
**必要なものだけを1つずつ挙げている**のが要点で、`*` で全部許すのとは意味が違う。

## 9. CloudFront ディストリビューション ＋ OAC

**ディストリビューション** … 配信そのもの。世界中のエッジに中身を配る。
**OAC（Origin Access Control）** … CloudFront だけが S3 を読めるようにする仕組み。

**ここが一番項目が多い。** 落ち着いて1つずつ。

### オリジン（配信元）

CloudFront → ディストリビューション → **ディストリビューションを作成**

| 項目 | 値 |
|---|---|
| オリジンドメイン | 手順6のバケットを選ぶ |
| オリジンアクセス | **Origin access control settings (recommended)** |
| Origin access control | 「**新しい OAC を作成**」→ 既定のまま作成（署名動作は SigV4） |

⚠️ **オリジンドメインの選び方に注意。** バケット名を入力欄に入れると、
候補が2つ出ることがある。

- `<バケット名>.s3.us-east-1.amazonaws.com` ← **こちらを選ぶ**
- `<バケット名>.s3-website-us-east-1.amazonaws.com` ← 静的ウェブサイトホスティング用。選ばない

⚠️ OAC を選ぶと「**バケットポリシーを更新する必要があります**」という案内と
「**ポリシーをコピー**」ボタンが出る。**このJSONを控えておく**（手順10で使う）。

### デフォルトのキャッシュビヘイビア

| 項目 | 値 |
|---|---|
| ビューワープロトコルポリシー | **Redirect HTTP to HTTPS** |
| 許可された HTTP メソッド | **GET, HEAD** |
| 自動オブジェクト圧縮 | **オン** |
| キャッシュポリシー | **CachingOptimized**（マネージド） |
| レスポンスヘッダーポリシー | **mitamo-kitchen-security-headers**（手順8） |

**関数の関連付け**（同じ画面の下のほう。「追加設定」の中にあることもある）

| イベントタイプ | 値 |
|---|---|
| ビューワーリクエスト | 関数タイプ **CloudFront Functions** → `rewrite-index` |

### ウェブアプリケーションファイアウォール (WAF)

「**セキュリティ保護を有効にしないでください**」を選ぶ。

> **なぜ使わないのか。** WAF は月額と従量課金がかかる。
> このサイトは静的HTMLで、フォームも外部（Google）に出しており、
> **攻撃されて壊れるものが無い**。費用に見合わないという判断。
> 「検討した上で使わない」ことも設計判断なので、記録に残す価値がある。

### 設定

| 項目 | 値 |
|---|---|
| 料金クラス | **北米、欧州、アジア、中東、アフリカを使用**（PriceClass 200） |
| デフォルトルートオブジェクト | `index.html` |
| HTTP バージョン | HTTP/2 と HTTP/3 |

「**ディストリビューションを作成**」を押す。

### カスタムエラーレスポンス（作成後）

作ったディストリビューションを開いて「**エラーページ**」タブ → 「**カスタムエラーレスポンスを作成**」を2回。

| HTTPエラーコード | エラーキャッシュ最小TTL | レスポンスページのパス | HTTPレスポンスコード |
|---|---|---|---|
| **403** | 300 | `/index.html` | **404** |
| **404** | 300 | `/index.html` | **404** |

> **なぜ403を404に読み替えるのか。** バケットが非公開なので、
> S3 は存在しないファイルに対して 403（権限が無い）を返す。
> そのまま出すと利用者には「見てはいけないものがある」ように見えるが、
> 実際は「そのページが無い」。**正しい意味で返す。**

### 待つ

ステータスが「**デプロイ中**」から「**有効**」に変わるまで **5〜15分**。
ここで一度手が空くので、コーヒーを淹れるとよい。

**ディストリビューションID**（`E` で始まる文字列）と
**ディストリビューションドメイン名**（`dxxxxxxxxxx.cloudfront.net`）をメモする。

## 10. S3 バケットポリシー

手順9でコピーしたポリシーを、バケットに貼る。

S3 → 手順6のバケット → 「**アクセス許可**」タブ → 「バケットポリシー」の**編集**

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipal",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::<バケット名>/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::<アカウントID>:distribution/<配信ID>"
      }
    }
  }]
}
```

`<...>` は自分の値に置き換える（コピーしたものには既に入っているはず）。

### ここが OAC の肝

バケットは誰にも公開されていない。それでも CloudFront は読める。
理由は、このポリシーが「**CloudFront というサービスからの読み取り**」を許しているから。

さらに `AWS:SourceArn` の条件で「**このディストリビューションから**」に絞っている。
**この条件が無いと、他人が作った CloudFront からもバケットを読めてしまう。**
手で書くときに忘れやすい箇所で、忘れても普通に動いてしまうので気づきにくい。

### ここで一度、動くか確かめる

リポジトリの根元で:

```bash
npm run build
aws s3 sync dist/ s3://<バケット名>/
```

`aws s3 sync` は、`dist/` の中身をバケットに写す。
成功すると `upload: ...` が46行ほど流れる。

ブラウザで `https://dxxxxxxxxxx.cloudfront.net` を開いて、5つ確認する。

- [ ] トップが出る
- [ ] **`/en/` が英語トップを返す** ← CloudFront Function が効いている証拠
- [ ] `/recipes.html` が開く
- [ ] 存在しないURL（`/nothing.html`）が 404 を返す
- [ ] 開発者ツール（F12）→ Network → 一番上の項目 → Headers →
      レスポンスヘッダーに `content-security-policy` が乗っている

**ここが全部通れば、OAC も Function もヘッダーポリシーも正しく効いている。**

### うまくいかないとき

| 症状 | たいていの原因 |
|---|---|
| AccessDenied が出る | バケットポリシーが貼れていない／`<...>` が置き換わっていない |
| `/en/` で 404 | 手順7の**発行**を忘れている、または関数を関連付けていない |
| 古い内容が出る | CloudFront のキャッシュ。`?v=2` を付けて開くと確かめられる |
| CSP ヘッダーが無い | 手順8のポリシーをビヘイビアに紐付けていない |

## 11. OIDC プロバイダ

### これは何をするものか

GitHub Actions から AWS を操作したい。
素朴にやるなら、アクセスキーを発行して GitHub に保存する。
**でもそれは、鍵をコピーして置いておくということ**で、漏れたら終わり。

**OIDC** は鍵を置かない方法。GitHub が「これは TrueAburis/mitamo-kitchen の
main ブランチから来た実行です」という署名付きの証明書を出し、
AWS がそれを検証して、**その場限りの資格情報**を渡す。

### 作る

IAM → 左メニューの「**ID プロバイダ**」 → **プロバイダを追加**

| 項目 | 値 |
|---|---|
| プロバイダのタイプ | **OpenID Connect** |
| プロバイダの URL | `https://token.actions.githubusercontent.com` |
| 対象者（Audience） | `sts.amazonaws.com` |

URL を入れたあと「**サムプリントを取得**」が要求されたら押す
（最近のコンソールは自動で取る）。

⚠️ **すでに同じURLのプロバイダがあるとエラーになる。**
その場合は新規作成せず、既存のものをそのまま使う（手順12の信頼ポリシーは変わらない）。

## 12. IAM ロール

**ロール** … 「誰か」ではなく「役割」。
人やサービスが**一時的に借りる**権限のまとまり。

### 信頼ポリシー（誰が借りてよいか）

IAM → ロール → **ロールを作成**

「信頼されたエンティティタイプ」で「**カスタム信頼ポリシー**」を選び、これを貼る。

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::<アカウントID>:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
      },
      "StringLike": {
        "token.actions.githubusercontent.com:sub": "repo:TrueAburis/mitamo-kitchen:ref:refs/heads/main"
      }
    }
  }]
}
```

`<アカウントID>` は手順5で控えた12桁。

次の「許可を追加」の画面は**何も選ばずに次へ**（あとでインラインポリシーを付ける）。

- ロール名：`mitamo-kitchen-deploy`
- 説明：`Deploy role for GitHub Actions`（**日本語は使えない**）

### 権限（借りたら何ができるか）

作ったロールを開いて「**許可を追加**」→「**インラインポリシーを作成**」→ **JSON** タブ

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::<バケット名>/*"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetBucketLocation"],
      "Resource": "arn:aws:s3:::<バケット名>"
    },
    {
      "Effect": "Allow",
      "Action": "cloudfront:CreateInvalidation",
      "Resource": "arn:aws:cloudfront::<アカウントID>:distribution/<配信ID>"
    }
  ]
}
```

ポリシー名：`deploy-to-s3-and-invalidate`

⚠️ **`Resource` が2つに分かれている理由。**
`arn:aws:s3:::バケット名/*` は「中のファイル」、
`arn:aws:s3:::バケット名` は「バケットそのもの」。
`aws s3 sync` は中身の一覧を取るので、**両方いる**。
片方だけだと sync が途中で失敗する。

### 最大セッション時間を短くする

ロールの「概要」で「**編集**」→ 最大セッション時間を **1時間**にする。

### なぜこの形なのか（設計の見どころ）

アクセスキーを発行して GitHub に保存する方法を取っていない。
**鍵がどこにも保存されないので、漏れようがない。**

`sub` を `repo:TrueAburis/mitamo-kitchen:ref:refs/heads/main` に絞っているのが要点。

- ここを `repo:TrueAburis/mitamo-kitchen:*` と緩めると、
  **他人が送ってきたプルリクエストからこのロールを使えてしまう**
- ブランチまで指定することで、main に入ったものだけが公開できる
